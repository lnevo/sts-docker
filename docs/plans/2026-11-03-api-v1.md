# STS API v1: contract

Written 2026-11-03. This is the contract the API, the helpers and the agent
tooling build against. Change it here first.

## As built (2026-11-03)

Differences from the original contract, which the sections below already
reflect:

- The destructive catalog ids that need `admin` are `restore_database`,
  `backup_database`, `wipe_database`, `reset_session` and `restart_session`.
- These commands always run as tasks: `generate_switchlists`,
  `render_switchlists`, `save_switchlist_cache`, `generate_waybills`,
  `generate_station_report`, `generate_wheel_report` and
  `rebuild_switchlists_index`. Flow-control ids such as `stop` return 422.
- Restore drops every table first (`full`, default true), runs
  `sts_restore_sql_file()`, then calls the existing `session_reset_hooks` with
  `reason: restore`. There is no separate `after_restore` hook.
- `PATCH /jobs` writes only `description`; renaming a job would orphan its step
  table. `PUT /settings/session_nbr` returns 422; use `/session/advance`
  instead.
- `POST /admin/backups` runs synchronously and returns 201.
- Warm start, begin and play accept generic `config` and `options` objects.
  `tracked` needs the railroad plugin to register `tracked_overrides`.
- Review fixes (2026-11-03):
  - Recipes with destructive commands (the five ids above, checked on the
    normalized recipe, disabled steps included) can only be saved by an admin
    (`PUT /workflows/{name}`) or run by one (`POST /workflows/{name}/run`): 403
    naming the step numbers. The workflow_run task re-checks the file when it
    starts (`spec.allow_destructive` is true only for an admin caller). The
    stock `hart_session` and `start_session` workflows contain
    `restore_database` and `backup_database`, so they are admin-only to run.
  - Origin check: a non-GET/HEAD/OPTIONS request with an `Origin` whose
    host:port differs from `Host` is 403 (legacy routes too); CORS `*` only for
    GET/HEAD.
  - Maintenance lock: while an exclusive task is queued or running, other write
    routes answer 409 `maintenance task <id> running` (token routes and
    `POST /admin/tasks/{id}/fail` excepted). Writes hold a shared lock on
    `tasks/.maint.lock` for the request; exclusive task creation takes it
    exclusively plus the tasks lock, so the check and create are atomic.
    `POST /admin/backups` is a guarded write. Destructive commands always run as
    an exclusive task (202), also without `async`.
  - Tasks: `GET /tasks` and `GET /tasks/{id}` need `operator` (never opened by
    `STS_API_READ_OPEN`). Task records carry `pid_start`. `start.sh` runs
    `bin/fail_tasks.php` (queued/running become failed, "container restarted").
    New `POST /admin/tasks/{id}/fail` (admin, `force` for a live process). The
    newest 200 tasks and logs are kept (pruned on create).
  - Query values that are arrays are 422. Bad workflow names are 422 on read,
    run, put and delete. `POST /cars` takes an optional `id` (409 if taken).
  - Unload/load re-read the status `FOR UPDATE` and 409 on a lost race, as does
    an `UPDATE` that changes no row; a missing `car_orders` row on unload is
    fine, as in `load_unload.php`. Reposition waybills take the max numeric
    suffix of `NNN-E%` (two digits below 100, more after). Workflow saves are
    temp file + rename.
  - Token and task files are created with umask 0027; the token CLI chowns to
    www-data when run as root (use `docker exec -u www-data`); bootstrap runs
    under the token lock and writes its file via temp file + chmod + rename.
  - Not done: the optional `timeout_seconds` wall-clock cap (the runner has no
    supervisor process; needs a watchdog).
- Seeded API runs of warm start and of a workflow produce the same database as
  the CLIs `simulate_warm_start.php` and `run_catalog_workflow.php` (sandbox,
  seed 42, masked dump diff empty).

## Goals

- One standard base URL: `/sts/api/v1/`. Resource-shaped JSON over HTTP.
- An OpenAPI 3.1 spec at `/sts/api/v1/openapi.json` and Swagger UI at
  `/sts/api/docs/`, using the vendored swagger-ui. No CDN.
- Token auth with basic RBAC. Tokens are managed through the API.
- Enough coverage that `sts-helpers` can drive STS through HTTP instead of
  `docker exec php` and raw SQL. The exceptions are container lifecycle, parity
  dumps, host file moves and the dev-only sweep/diagnostic scripts.
- An agent plugin (skill, MCP server, agents) in this repo under `agent/`.
- Old URLs keep working: `/sts/api/index.php/wagon/...` and `/sts/api/wagon/...`
  with their old response shapes, plus `operational_steps_api.php` and the AJAX
  endpoints the web pages use.

## Serving

- `docker/apache-sts-api.conf` is copied into `/etc/apache2/conf-enabled/` by
  the Dockerfile. It sets `FallbackResource /sts/api/index.php` on
  `/var/www/html/sts/api`, so any path under `/sts/api/` that isn't a real file
  reaches the router with `REQUEST_URI` intact. mod_rewrite is not needed, and
  the dead `.htaccess` goes.
- `sts/api/index.php` routes by method plus path pattern from a route registry.
  Each `sts/api/v1/routes_*.php` file registers its routes with
  `api_route($method, $pattern, $handler, $role, $opts)`. Patterns use `{name}`
  segments. The legacy wagon routes are registered on top of the same handlers,
  using the legacy response formatter.
- Every request runs inside output buffering. Stray output, such as `open_db()`
  migration prints or notices, is discarded and logged to stderr, never mixed
  into JSON. Error reporting is `E_ALL` to the log and off for display.
- CORS: `Access-Control-Allow-Origin: *`, methods
  `GET, POST, PUT, PATCH, DELETE, OPTIONS`, headers
  `Authorization, Content-Type`. OPTIONS returns 204.

## Responses

- Success: `{"data": <value>, "meta": {...}}`. `meta` is optional and holds
  `total`, `limit` and `offset` for lists.
- Error: `{"error": {"code": "<slug>", "message": "<text>"}}`. The status codes
  are 400 `bad_request`, 401 `unauthorized`, 403 `forbidden`, 404 `not_found`,
  405 `method_not_allowed`, 409 `conflict`, 422 `invalid`, 500 `internal`. A 500
  never echoes SQL or exception internals; those go to the log.
- Lists take `limit` (default 100, max 1000) and `offset`, plus the per-resource
  filters below.
- Long-running work returns
  `202 {"data": {"task_id": "...", "status": "queued"}}` (see Tasks).

## Auth and RBAC

- Header: `Authorization: Bearer <token>`. Tokens look like `sts_` followed by
  40 hex characters.
- Roles are hierarchical: `reader` < `operator` < `editor` < `admin`.
  - `reader`: every GET.
  - `operator`: operating moves. That covers catalog commands that aren't
    destructive, car load/unload/reposition, advancing the session and running
    workflows.
  - `editor`: data edits (PATCH/POST on cars, jobs, shipments, ownership,
    settings) and saving or deleting workflows.
  - `admin`: backup, restore, warm start, begin or play a session, the
    destructive catalog commands (see As built) and token management.
- Policy is set by env on the web service:
  - `STS_API_READ_OPEN=1` (default): GETs need no token. Set it to `0` to
    require `reader`.
  - `STS_API_LEGACY_OPEN=1` (default): the legacy wagon routes keep working
    without a token, so RFID scanners keep working. Set it to `0` to require
    `operator`.
  - `GET /v1/health`, `GET /v1/openapi.json` and `/sts/api/docs/` are always
    open.
- Storage lives outside the web root and outside the database, so a seed restore
  can't wipe it. The file is `/var/lib/sts/api_tokens.json`, a new bind mount of
  `../sts-docker-data/config` (the sandbox uses `${STS_SANDBOX_DATA}/config`).
  It holds `{id, name, role, sha256, created_at, last_used_at, revoked_at}`.
  Only the hash is stored. The token is shown once, when it is created.
- Bootstrap: on start, `start.sh` writes `/var/lib/sts/bootstrap_admin.token`
  (mode 640, owned by www-data) if the token file has no active admin token. The
  token in it is a stored admin token named `bootstrap`. The helpers read it
  from the host side of the mount. `STS_API_ADMIN_TOKEN`, if set in the
  environment, is also accepted as admin and is not stored; use it for CI.
- CLI, run as www-data inside the web container:

  ```bash
  docker exec -u www-data sts-docker-web-1 \
    php /var/www/html/sts/api/bin/tokens.php list
  # also: create <name> <role> | revoke <id>
  ```

## Routes

Every path below is under `/sts/api/v1`. `{car}` accepts an id, reporting marks,
or the RFID code. `{location}` accepts an id or a location code. `{job}` accepts
an id or a name.

### Open

- `GET /health`: `{status, version, stack, session_nbr, db: ok|error}`. `stack`
  comes from `STS_STACK_NAME`: `live` by default, `sandbox` in the sandbox
  compose.
- `GET /openapi.json`: the merged spec (see OpenAPI below).

### reader

- `GET /session`: the current session number plus the operations hub counts from
  `operations_get_stats()`.
- `GET /settings`, `GET /settings/{name}`
- `GET /cars` with filters `status`, `location`, `job`, `car_code`, `marks`
  (prefix). `GET /cars/{car}`, `GET /cars/{car}/history`.
- `GET /locations` with filter `station`. `GET /locations/{location}` includes
  the cars there.
- `GET /stations` (the `routing` table), `GET /stations/{id}`
- `GET /jobs`, `GET /jobs/{job}` includes its steps, pickup criteria and
  assigned cars.
- `GET /shipments`, `GET /shipments/{id}`, `GET /commodities`, `GET /car-codes`,
  `GET /owners`, `GET /ownership`
- `GET /car-orders` with filter `status` (`unfilled`, `filled`, `all`) and
  `shipment`. `GET /car-orders/{waybill}`.
- `GET /catalog`: the operational steps catalog, the same data as
  `operational_steps_api.php?action=catalog`.
- `GET /workflows`, `GET /workflows/{name}`: the recipe JSON.
- `GET /sessions`: session output directories and manifests. `GET /sessions/{n}`
  is one session's manifest, plus URLs for its switch lists and waybills.
- `GET /backups`: backup files with name, size and mtime.
- `GET /tasks`, `GET /tasks/{id}`

### operator

- `POST /commands/{command}` with body
  `{params: {...}, async?: bool, seed?: int}`. It runs one catalog command
  through `operational_steps_dispatch_step()`. `{command}` must be a catalog id;
  the four destructive ids need `admin`. With `async`, or for commands marked
  slow, the response is 202 with a task.
- `POST /cars/{car}/load`, `POST /cars/{car}/unload`,
  `POST /cars/{car}/reposition {location}`. These are the wagon handlers.
- `POST /session/advance`: increment the session (`increment_session`).
- `POST /workflows/{name}/run`
  `{seed?, start_step?, stop_step?, skip?, sections?, session_count?, render?: bool}`
  always runs as a task, through `session_run_recipe()`.

### editor

- `PATCH /cars/{car}`, `POST /cars`, `PATCH /jobs/{job}`,
  `PATCH /shipments/{id}`, `PUT /ownership/{car}`, `PUT /settings/{name}`.
  Writable columns are whitelisted per entity, and every query is a prepared
  statement.
- `PUT /workflows/{name}`, `DELETE /workflows/{name}`

### admin

- `POST /admin/backups {name}`: `backup_tables()`.
- `POST /admin/restore {backup, photos?: bool}`. It runs as a task:
  `sts_restore_sql_file()`, then copies photos from `backups/<name>_photos` when
  asked, then calls `session_reset_hooks` (`reason: restore`). Core names no
  plugin.
- `POST /admin/warm-start {sessions, max_sessions, seed, backup?, continue?, tracked?}`
  runs as a task through `warm_start_run()`.
- `POST /admin/sessions/begin {...}` and `POST /admin/sessions/play {...}` run
  as tasks through `warm_start_begin_operating_session()` and
  `warm_start_play_operating_session()`. Any railroad-specific choice is a
  request parameter, never a name in core.
- `GET /admin/tokens`, `POST /admin/tokens {name, role}` (returns the token
  once), `DELETE /admin/tokens/{id}`

## Tasks

- A task is a JSON spec under `/var/lib/sts/tasks/<id>.json` plus a `.log`. The
  router writes the spec, then starts
  `php /var/www/html/sts/api/bin/run_task.php <id>` detached (`nohup … &`, as
  www-data).
- The runner sets `mt_srand(seed)` and `STS_SIM_SEED` when a seed is given,
  calls the same core functions the CLIs call, and records status (`queued`,
  `running`, `succeeded`, `failed`), `started_at`, `finished_at`, `result`
  (including `session_nbr` before and after) and `error`.
- `GET /tasks/{id}?log=200` returns the status plus the last N log lines. Only
  one admin task runs at a time per stack; another request gets 409 `conflict`
  while one is running.

## OpenAPI

- The spec is in fragments under `sts/api/openapi/*.json` (`base`, `read`,
  `operate`, `edit`, `admin`). `GET /v1/openapi.json` merges their `paths` and
  `components` at request time and injects the catalog command ids as the enum
  for `{command}`. One fragment per builder keeps parallel work from colliding.
- The spec declares `bearerAuth` and states each operation's role in
  `x-sts-role` and the description. `servers` is `/sts/api/v1`, relative, so it
  works on 8980 and 8981.
- `/sts/api/docs/index.html` loads `../../vendor/swagger-ui/*` and points at
  `../v1/openapi.json`, with `persistAuthorization` on.

## Clients

- **Helpers** (`sts-helpers`): `lib/sts_api.sh` (curl plus python3 for JSON) and
  `lib/sts_api.py`.
  - `STS_API_URL` defaults from `COMPOSE_PROJECT_NAME`: `sts-sandbox` maps to
    `http://localhost:8981/sts/api/v1`, anything else to port 8980.
  - `STS_API_TOKEN` defaults to the bootstrap token file under the matching data
    dir.
  - `sts_task_wait` polls a task until it finishes.
- **Agent plugin** (`sts-docker/agent/`): `.claude-plugin/plugin.json`,
  `.mcp.json`, `servers/sts_api.py` (stdlib only, the same `mcp_stdio` shape as
  model-railroad-skills), `skills/sts-api/SKILL.md`, `agents/sts-operator.md`
  and `agents/sts-inspector.md`, and `tests/`.
  - It reads `STS_API_URL` and `STS_API_TOKEN`.
  - Each tool sets `readOnlyHint` and `destructiveHint` honestly.
  - The repo root gets `.claude-plugin/marketplace.json` pointing at `./agent`.

## Phase 2: browser sign-in, policy, editor on v1

Added 2026-11-03.

### Browser sign-in

- `POST /v1/auth/login {token}` checks the token and starts a server-side
  session. The browser gets an HttpOnly cookie `sts_api` (SameSite=Strict,
  Path=/sts/, 12-hour idle timeout) that holds only a random session id. The
  token itself never reaches page JavaScript storage.
- `GET /v1/auth/me` returns `{name, role, expires_at}`, or 401.
  `POST /v1/auth/logout` ends the session.
- Every request rechecks the session's token, so revoking a token ends its
  sessions immediately. Bearer tokens keep working for scripts. The existing
  Origin check covers cookie-authenticated writes.
- As built after review: the cookie is `sts_api_<stack>` (STS_STACK_NAME, else the
  published port); sessions also end 7 days after login; a new login replaces
  that browser's session id and keeps other sessions; the failed-login limiter
  is one locked check-and-record with at most 2000 files kept.
- `api_web_user(): ?array` (cookie or bearer) and
  `api_role_allows(?array $user, string $role): bool` in `lib/auth.php` are the
  shared helpers. Legacy pages use them too.

### Policy

- `/var/lib/sts/api_policy.json` holds:
  - `command_roles`: the minimum role per catalog command id.
  - `read_open`, `legacy_open` and `editor_open`. When set, these override the
    environment defaults.
- Default command roles:
  - `admin`: `restore_database`, `wipe_database`, `reset_session`, `remove_backup`.
  - `protected_backups` (default `*seed*`, `*_locked*`): non-admin callers may
    not overwrite an existing backup matching a pattern.
  - A corrupt or unreadable policy file is logged; commands then all need admin
    and the flags use their env defaults.
  - `operator`: `backup_database`, `restart_session`, and every other command.
- `GET /v1/admin/policy` and `PUT /v1/admin/policy` (admin).
  `api_command_required_role(string $id): string` in `lib/policy.php` is the
  only place the role is looked up.

### Workflow runs check each step as it runs

- `session_run_recipe()` gets an optional `before_dispatch` callable in
  `$options`. When it is unset, behaviour is unchanged. The workflow-run task
  passes a guard that fails the run at the first step whose command needs a
  higher role than the caller has, and names that step.
- Steps skipped by conditions or ranges are never checked. An operator can
  therefore run `hart_session` past session 0, where the restore step is
  skipped. At session 0 the run stops at that step with a 403-style task error.
- As built after review: the guard is threaded through every recipe path
  (`run_switchlists` play-after, `operational_steps_run_recipe_steps`, legacy
  `sts_before_dispatch`); `editor_open` still installs it as operator. Runs
  (v1 and legacy) are refused with 403 before any dispatch when an enabled,
  in-range, non-conditional step needs more than the caller's role. Legacy runs
  take the shared maintenance lock (409 during an exclusive task).
  `timeout_seconds` is at least 60 for non-admins. Timed tasks run the child in
  its own process group, which is killed on timeout or admin fail; the task
  stores `child_pid`. A task whose creator's token was revoked fails "token
  revoked" instead of starting. `DELETE /sessions/output` is editor and takes
  the exclusive maintenance lock. A restore writes
  `/var/lib/sts/restore_in_progress`; `open_db()` skips its migrations and v1
  answers 503 `maintenance` (except health, openapi, tasks, auth) while it exists.
- Saving a workflow no longer blocks recipes that contain admin steps. Saving
  doesn't run anything.

### Editor endpoints on v1

These are the editor's remaining actions:

- `POST /workflows/compile` (reader)
- `POST /workflows/normalize` (reader)
- `POST /workflows/import` (editor)
- `GET /workflows/active` (reader) and `PUT /workflows/active` (editor)
- `GET /workflows/{name}/run-options` (reader)
- `GET /workflows/{name}/download` (reader; raw file)
- `POST /sessions/{n}/rerender` (operator)
- `POST /sessions/{n}/print-all` (operator)
- `GET /simulator/status` (reader)

Each covers the matching `operational_steps_api.php`, `simulator_api.php` or
`save_operational_steps.php` action. Runs still go through
`POST /workflows/{name}/run`; the editor polls the task log.

With `editor_open=false` (the default), those three legacy files answer reads
but refuse writes and runs unless `api_web_user()` has the needed role.

### Remaining gaps

- `DELETE /sessions/output` (operator) clears the generated switch-list output
  directory.
- `GET /locations/{code}` resolves location aliases a plugin registers through
  the warm-start scenario's `location_aliases`.
- Tasks accept `timeout_seconds`. The runner executes the task in a child
  process and kills it on expiry, and the task is marked failed with "timed
  out".

### Administration page

`sts/api_admin.php`, linked from `db-maint.html` and the editor navbar, signs in
with a token. With an admin token it can:

- list, create (the secret is shown once, with a copy button) and revoke tokens;
- edit the policy (command roles, the open flags);
- list tasks and fail a stuck one.
