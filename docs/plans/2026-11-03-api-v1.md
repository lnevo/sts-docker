# STS API v1: contract

Written 2026-11-03. This is the contract the API, the helpers and the agent
tooling build against. Change it here first.

## Goals

- One standard base URL: `/sts/api/v1/`. Resource-shaped JSON over HTTP.
- An OpenAPI 3.1 spec at `/sts/api/v1/openapi.json` and Swagger UI at
  `/sts/api/docs/`, using the vendored swagger-ui. No CDN.
- Token auth with basic RBAC. Tokens are managed through the API.
- Enough coverage that `sts-helpers` can drive STS through HTTP instead of
  `docker exec php` and raw SQL. The exceptions are container lifecycle,
  parity dumps, host file moves and the dev-only sweep/diagnostic scripts.
- An agent plugin (skill, MCP server, agents) in this repo under `agent/`.
- Old URLs keep working: `/sts/api/index.php/wagon/...` and
  `/sts/api/wagon/...` with their old response shapes, plus
  `operational_steps_api.php` and the AJAX endpoints the web pages use.

## Serving

- `docker/apache-sts-api.conf` is copied into `/etc/apache2/conf-enabled/`
  by the Dockerfile. It sets `FallbackResource /sts/api/index.php` on
  `/var/www/html/sts/api`, so any path under `/sts/api/` that isn't a real
  file reaches the router with `REQUEST_URI` intact. mod_rewrite is not
  needed, and the dead `.htaccess` goes.
- `sts/api/index.php` routes by method plus path pattern from a route
  registry. Each `sts/api/v1/routes_*.php` file registers its routes with
  `api_route($method, $pattern, $handler, $role, $opts)`. Patterns use
  `{name}` segments. The legacy wagon routes are registered on top of the
  same handlers, using the legacy response formatter.
- Every request runs inside output buffering. Stray output, such as
  `open_db()` migration prints or notices, is discarded and logged to
  stderr, never mixed into JSON. Error reporting is `E_ALL` to the log and
  off for display.
- CORS: `Access-Control-Allow-Origin: *`, methods
  `GET, POST, PUT, PATCH, DELETE, OPTIONS`, headers
  `Authorization, Content-Type`. OPTIONS returns 204.

## Responses

- Success: `{"data": <value>, "meta": {...}}`. `meta` is optional and holds
  `total`, `limit` and `offset` for lists.
- Error: `{"error": {"code": "<slug>", "message": "<text>"}}`. The status
  codes are 400 `bad_request`, 401 `unauthorized`, 403 `forbidden`,
  404 `not_found`, 405 `method_not_allowed`, 409 `conflict`,
  422 `invalid`, 500 `internal`. A 500 never echoes SQL or exception
  internals; those go to the log.
- Lists take `limit` (default 100, max 1000) and `offset`, plus the
  per-resource filters below.
- Long-running work returns `202 {"data": {"task_id": "...", "status": "queued"}}`
  (see Tasks).

## Auth and RBAC

- Header: `Authorization: Bearer <token>`. Tokens look like `sts_` followed
  by 40 hex characters.
- Roles are hierarchical: `reader` < `operator` < `editor` < `admin`.
  - `reader`: every GET.
  - `operator`: operating moves. That covers catalog commands that aren't
    destructive, car load/unload/reposition, advancing the session and
    running workflows.
  - `editor`: data edits (PATCH/POST on cars, jobs, shipments, ownership,
    settings) and saving or deleting workflows.
  - `admin`: backup, restore, warm start, begin or play a session, the
    destructive catalog commands (`restore_database`, `wipe`, `reset`,
    `backup_database`) and token management.
- Policy is set by env on the web service:
  - `STS_API_READ_OPEN=1` (default): GETs need no token. Set it to `0` to
    require `reader`.
  - `STS_API_LEGACY_OPEN=1` (default): the legacy wagon routes keep working
    without a token, so RFID scanners keep working. Set it to `0` to require
    `operator`.
  - `GET /v1/health`, `GET /v1/openapi.json` and `/sts/api/docs/` are always
    open.
- Storage lives outside the web root and outside the database, so a seed
  restore can't wipe it. The file is `/var/lib/sts/api_tokens.json`, a new
  bind mount of `../sts-docker-data/config` (the sandbox uses
  `${STS_SANDBOX_DATA}/config`). It holds
  `{id, name, role, sha256, created_at, last_used_at, revoked_at}`. Only the
  hash is stored. The token is shown once, when it is created.
- Bootstrap: on start, `start.sh` writes
  `/var/lib/sts/bootstrap_admin.token` (mode 640, owned by www-data) if the
  token file has no active admin token. The token in it is a stored admin
  token named `bootstrap`. The helpers read it from the host side of the
  mount. `STS_API_ADMIN_TOKEN`, if set in the environment, is also accepted
  as admin and is not stored; use it for CI.
- CLI: `docker exec sts-docker-web-1 php /var/www/html/sts/api/bin/tokens.php
list|create <name> <role>|revoke <id>`.

## Routes

Every path below is under `/sts/api/v1`. `{car}` accepts an id, reporting
marks, or the RFID code. `{location}` accepts an id or a location code.
`{job}` accepts an id or a name.

### Open

- `GET /health`: `{status, version, stack, session_nbr, db: ok|error}`.
  `stack` comes from `STS_STACK_NAME`: `live` by default, `sandbox` in the
  sandbox compose.
- `GET /openapi.json`: the merged spec (see OpenAPI below).

### reader

- `GET /session`: the current session number plus the operations hub
  counts from `operations_get_stats()`.
- `GET /settings`, `GET /settings/{name}`
- `GET /cars` with filters `status`, `location`, `job`, `car_code`,
  `marks` (prefix). `GET /cars/{car}`, `GET /cars/{car}/history`.
- `GET /locations` with filter `station`. `GET /locations/{location}`
  includes the cars there.
- `GET /stations` (the `routing` table), `GET /stations/{id}`
- `GET /jobs`, `GET /jobs/{job}` includes its steps, pickup criteria and
  assigned cars.
- `GET /shipments`, `GET /shipments/{id}`, `GET /commodities`,
  `GET /car-codes`, `GET /owners`, `GET /ownership`
- `GET /car-orders` with filter `status` (`unfilled`, `filled`, `all`) and
  `shipment`. `GET /car-orders/{waybill}`.
- `GET /catalog`: the operational steps catalog, the same data as
  `operational_steps_api.php?action=catalog`.
- `GET /workflows`, `GET /workflows/{name}`: the recipe JSON.
- `GET /sessions`: session output directories and manifests.
  `GET /sessions/{n}` is one session's manifest, plus URLs for its switch
  lists and waybills.
- `GET /backups`: backup files with name, size and mtime.
- `GET /tasks`, `GET /tasks/{id}`

### operator

- `POST /commands/{command}` with body
  `{params: {...}, async?: bool, seed?: int}`. It runs one catalog command
  through `operational_steps_dispatch_step()`. `{command}` must be a catalog
  id; the four destructive ids need `admin`. With `async`, or for commands
  marked slow, the response is 202 with a task.
- `POST /cars/{car}/load`, `POST /cars/{car}/unload`,
  `POST /cars/{car}/reposition {location}`. These are the wagon handlers.
- `POST /session/advance`: increment the session (`increment_session`).
- `POST /workflows/{name}/run`
  `{seed?, start_step?, stop_step?, skip?, sections?, session_count?, render?: bool}`
  always runs as a task, through `session_run_recipe()`.

### editor

- `PATCH /cars/{car}`, `POST /cars`, `PATCH /jobs/{job}`,
  `PATCH /shipments/{id}`, `PUT /ownership/{car}`, `PUT /settings/{name}`.
  Writable columns are whitelisted per entity, and every query is a
  prepared statement.
- `PUT /workflows/{name}`, `DELETE /workflows/{name}`

### admin

- `POST /admin/backups {name}`: `backup_tables()`.
- `POST /admin/restore {backup, photos?: bool}`. It runs as a task:
  `sts_restore_sql_file()`, then copies photos from `backups/<name>_photos`
  when asked, then calls the generic plugin hook `after_restore`. Core names
  no plugin.
- `POST /admin/warm-start {sessions, max_sessions, seed, backup?, continue?, tracked?}`
  runs as a task through `warm_start_run()`.
- `POST /admin/sessions/begin {...}` and `POST /admin/sessions/play {...}`
  run as tasks through `warm_start_begin_operating_session()` and
  `warm_start_play_operating_session()`. Any railroad-specific choice is a
  request parameter, never a name in core.
- `GET /admin/tokens`, `POST /admin/tokens {name, role}` (returns the token
  once), `DELETE /admin/tokens/{id}`

## Tasks

- A task is a JSON spec under `/var/lib/sts/tasks/<id>.json` plus a `.log`.
  The router writes the spec, then starts
  `php /var/www/html/sts/api/bin/run_task.php <id>` detached
  (`nohup … &`, as www-data).
- The runner sets `mt_srand(seed)` and `STS_SIM_SEED` when a seed is given,
  calls the same core functions the CLIs call, and records status
  (`queued`, `running`, `succeeded`, `failed`), `started_at`, `finished_at`,
  `result` (including `session_nbr` before and after) and `error`.
- `GET /tasks/{id}?log=200` returns the status plus the last N log lines.
  Only one admin task runs at a time per stack; another request gets
  409 `conflict` while one is running.

## OpenAPI

- The spec is in fragments under `sts/api/openapi/*.json` (`base`, `read`,
  `operate`, `edit`, `admin`). `GET /v1/openapi.json` merges their `paths`
  and `components` at request time and injects the catalog command ids as the
  enum for `{command}`. One fragment per builder keeps parallel work from
  colliding.
- The spec declares `bearerAuth` and states each operation's role in
  `x-sts-role` and the description. `servers` is `/sts/api/v1`, relative,
  so it works on 8980 and 8981.
- `/sts/api/docs/index.html` loads `../../vendor/swagger-ui/*` and points at
  `../v1/openapi.json`, with `persistAuthorization` on.

## Clients

- **Helpers** (`sts-helpers`): `lib/sts_api.sh` (curl plus python3 for
  JSON) and `lib/sts_api.py`.
  - `STS_API_URL` defaults from `COMPOSE_PROJECT_NAME`: `sts-sandbox` maps
    to `http://localhost:8981/sts/api/v1`, anything else to port 8980.
  - `STS_API_TOKEN` defaults to the bootstrap token file under the matching
    data dir.
  - `sts_task_wait` polls a task until it finishes.
- **Agent plugin** (`sts-docker/agent/`): `.claude-plugin/plugin.json`,
  `.mcp.json`, `servers/sts_api.py` (stdlib only, the same `mcp_stdio`
  shape as model-railroad-skills), `skills/sts-api/SKILL.md`,
  `agents/sts-operator.md` and `agents/sts-inspector.md`, and `tests/`.
  - It reads `STS_API_URL` and `STS_API_TOKEN`.
  - Each tool sets `readOnlyHint` and `destructiveHint` honestly.
  - The repo root gets `.claude-plugin/marketplace.json` pointing at
    `./agent`.
